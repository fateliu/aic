# 三人团队分工与验收

这是建议任务单，按实际成员能力领取。下面“待做”均未替成员完成；成员应留下自己的修改、测试记录和解释，不能只在材料里挂名字。第一轮先把一个校园创作场景演示稳，再扩展更多模型和视频。

## 分工总览

| 角色 | 负责的结果 | 主要目录 | 本轮不需要承担 |
| --- | --- | --- | --- |
| 项目负责人（你） | 产品取舍、视觉体验、真实样例、集成验收与答辩主线 | src、public、README、比赛文档 | 一个人包办全部测试记录 |
| 后端同学 | API 稳定性、图片任务恢复、存储与模型服务边界 | server.mjs、lib、test | 重做整套前端或同时换技术栈 |
| 测试与演示同学（编程新手） | 可复现的问题单、素材来源、用户试用、演示素材 | docs/qa、经确认的 docs/examples | 调模型协议、处理密钥、直接改服务器 |

新手不是“随便写一份 PPT”。流程测试和真实应用证据会直接影响产品完整性与答辩可信度，是有独立交付物的工作。

## 负责人：先完成三件事

1. 确定唯一主演示：例如“社团宣传插画 + 原创四格故事”。冻结一次演示所用的题材、角色和输出范围。
2. 在红蓝主题与角色素材上做最终选择；接收测试同学的手机问题，安排修复。真实图片调用预算由你控制，账号不要交给全组共用。
3. 审核两个队友的交付与 PR，完成整套流程录屏，能解释主子 Agent、Skill、版本和图片任务的关系。

验收：另一位同学按文档能启动，能从想法走到导出；演示与报告对模型来源、模拟数据和未完成功能表述一致。

## 后端同学：按顺序领取

| 编号 | 待做任务 | 可检查的交付物 | 完成标准 |
| --- | --- | --- | --- |
| B01 | 熟悉现有 API 与提供方边界 | 跑通测试和无密钥练习，提交一份接口理解/问题清单 | 能说明 create、refine、generate、approve、images、refresh 的差别，能用接口创建一个 demo 项目 |
| B02 | 加入服务端图片查询调度 | 新 worker 模块 + 接入 + 自动测试 | 收到 task_id 后关掉网页仍能查询保存；重启可继续；仅查询已有任务，不自动重新提交付费请求；与 HTTP 共用项目锁 |
| B03 | 提升错误可定位性 | 保持兼容的错误 code、日志和恢复测试 | 浏览器不显示密钥或上游敏感正文；能区分权限、余额、限流、下载失败、未知提交；旧 {error} 文案仍可用 |
| B04 | 调研演示部署 | 一页部署方案与运行清单 | 明确单机/在线选择、持久化位置、权限和备份；实际部署前与负责人确认，不把当前本机服务直接开放公网 |

建议一个 PR 完成一个编号。B02 是本轮主要工程任务；不要同时重写成另一个框架、数据库和微服务。当前 createApp 已支持注入 imageProvider，类型约定在 `lib/image-provider.d.ts`，契约见 [后端交接](backend-handoff.md)。

可选下一轮：真实漫画参考图质量联调、存储迁移、视频服务适配。先写方案和验收标准，再增加依赖。

## 测试与演示同学：即使不会编程也能开始

**第一步（当天）**：安装 Node 22.12+，按开发指南先执行 `npm ci`，再执行 `npm run dev:mock`。用一个原创题材跑通：填入示例→优化→确认→草稿→确认→模拟四格→合成下载。该端口不需要密钥，图像相同是正常现象。

| 编号 | 待做任务 | 交付物 | 完成标准 |
| --- | --- | --- | --- |
| Q01 | 跑人工测试清单 | 一份填写后的测试记录，保留日期/版本/浏览器 | 每条有通过/失败/未测，失败带步骤和截图；没有测试的不能填通过 |
| Q02 | 整理界面与演示素材 | 5–8 个候选素材及来源登记 | 文件名清楚，有来源/作者/用途/授权情况；不直接把来源不明素材写成原创 |
| Q03 | 收集真实试用反馈 | 3–5 位同学的匿名记录 | 经过同意，记录完成耗时、卡住步骤、修改/重生成次数和原话；不虚构用户 |
| Q04 | 演示录制与时间轴 | 3–5 分钟视频初稿 + 操作时间轴 | 文字可读，遮蔽账户/密钥，符合匿名要求；等待若剪辑需标注；模拟图片不冒充真实模型效果 |
| Q05 | 材料交叉检查 | 文件名、链接、大小、内容一致性检查表 | 能指出方案/视频/软件能力不一致之处；最终 PDF 和视频实际能打开 |

配套模板： [人工测试](qa/manual-checklist.md)、[问题单](qa/bug-template.md)、[素材表](qa/asset-register.md)、[试用记录](qa/user-feedback-template.md)、[演示脚本](demo-script.md)。不会提交 PR 时，先由负责人教一次；仍有困难可交文档和截图，由负责人代为合入并注明记录人。

## 一周推进建议

| 阶段 | 负责人 | 后端同学 | 测试同学 |
| --- | --- | --- | --- |
| 第 1 天 | 冻结主场景与视觉方向 | B01，了解契约 | Q01，先跑练习流程 |
| 第 2–3 天 | 修复交互与真实样例 | B02，任务恢复 | Q02，素材；整理首批问题 |
| 第 4–5 天 | 集成后端并验收 | B03，异常测试 | Q03，真实试用；真实调用由负责人操作 |
| 第 6–7 天 | 答辩主线与最终核验 | B04，部署说明 | Q04 / Q05，视频与材料检查 |

这只是排期建议，不是已经发生的工作记录。按成员实际时间缩放；每晚只同步“完成、遇到的问题、下一步”三项即可。

## 共同完成标准

提交的功能有复现步骤；改接口要同步文档；有影响的改动跑相关测试；不提交密钥和私人项目；真实模型结果与模拟夹具分开；本人能解释自己负责的实现或验证。涉及修改同一文件，先在团队里约好先后顺序。
